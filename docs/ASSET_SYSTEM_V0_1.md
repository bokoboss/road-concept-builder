# Asset System Architecture v0.1

## Goal

The product must not depend on the user manually drawing 2D assets, modelling 3D objects, or maintaining Illustrator/Blender workflows.

Assets should be generated, assembled, imported, normalized, and managed by the product/development pipeline as far as technically possible.

## Asset families

### 1. Procedural Road Components

Generated directly from engineering geometry.

Examples:
- traffic lanes;
- median;
- shoulder;
- curb;
- verge;
- sidewalk;
- bike lane;
- parking lane;
- barrier edge;
- channelizing island.

These are **not library graphics**. Their geometry is derived from semantic road data.

### 2. Procedural Markings

Parametric engineering markings generated by code.

Examples:
- solid line;
- dashed line;
- double line;
- stop line;
- yield line;
- zebra crossing;
- hatch/chevron/gore;
- parking stalls;
- warning bars;
- lane-use arrows;
- U-turn arrows;
- bike/motorcycle road stencils.

Example schema:

```ts
type LineMarkingStyle = {
  id: string;
  color: string;
  widthMeters: number;
  pattern: 'solid' | 'dashed' | 'double';
  dashLengthMeters?: number;
  gapLengthMeters?: number;
  standardRef?: StandardReference;
};
```

Markings must render consistently in 2D and 3D from the same parameters.

### 3. Semantic Assemblies

Configurable objects built from subcomponents.

Examples:
- traffic signs;
- signal assemblies;
- streetlights;
- overhead sign supports;
- bus stops;
- guardrail runs;
- bollard/delineator systems.

#### Sign assembly

```text
TrafficSign
  SignFace
    shape
    symbol/text
    color/style
  Support
    single pole
    double pole
    cantilever
    gantry
  Placement
    station/reference
    lateral offset
    orientation
    mounting height
```

The same sign face may be reused on different supports.

#### Signal assembly

```text
TrafficSignal
  pole
  mast arm
  vehicle heads[]
  pedestrian heads[]
  mounting/orientation metadata
```

V1 does not need signal timing simulation, but the assembly should be semantically structured.

### 4. Props

Reusable visual/context assets.

Examples:
- sedan;
- pickup/SUV;
- motorcycle;
- van;
- city bus;
- coach;
- rigid truck;
- articulated truck;
- trees;
- shrubs;
- people;
- benches;
- cones;
- simple structures.

A prop may provide multiple representations:

```ts
type AssetRepresentation = {
  plan2d?: string; // SVG/vector resource
  model3d?: string; // GLB/glTF resource
  thumbnail?: string;
};
```

A single semantic asset id is selected in both 2D and 3D.

### 5. Distribution Assets

Procedural placement rules for repeated assets.

Examples:
- tree row;
- streetlights along road edge;
- bollards along curb;
- delineators;
- barrier posts;
- parking objects;
- area vegetation.

Example:

```text
Place Along Edge
Asset        Street Light
Reference    Left sidewalk edge
Start        0+020
End          0+220
Spacing      25 m
Offset       0.50 m
Alternate    true
```

The distribution remains one semantic object until explicitly baked/exploded into individual props.

## Placement reference model

Road-related objects should prefer semantic attachment over free x/y placement.

Supported attachment concepts should include:
- world/local coordinates;
- road + station + lateral offset;
- lane + station;
- road edge + station + offset;
- junction/corner/approach reference;
- path reference;
- area/polygon reference.

When the road alignment changes, attached assets should move with the road unless detached intentionally.

## Asset metadata

Every library asset should carry machine-readable metadata.

Minimum:

```ts
type AssetMetadata = {
  id: string;
  version: string;
  name: string;
  category: string;
  tags: string[];
  dimensionsMeters?: {
    length?: number;
    width?: number;
    height?: number;
  };
  representations: AssetRepresentation;
  source: {
    origin: 'generated' | 'project' | 'third-party' | 'user-import';
    author?: string;
    url?: string;
  };
  license: {
    spdx?: string;
    attributionRequired: boolean;
    attributionText?: string;
  };
  standardRef?: StandardReference;
};
```

## Standards provenance

Engineering-sensitive assets must distinguish:
- geometry generated from an authoritative standard;
- agency manual/profile;
- international best practice;
- project assumption;
- custom concept;
- not yet verified.

A future `StandardReference` should include authority, document, edition/version, effective date, section/table/figure reference where appropriate, and applicability notes.

Do not represent unverified dimensions as official Thai standards.

## Thailand profile

Thailand should be a first-class standards/asset profile rather than a loose folder of images.

Initial source hierarchy to investigate and register:
- Department of Highways (DOH) — traffic signs, pavement markings, signals/safety devices, lighting and highway guidance;
- Department of Rural Roads (DRR) — applicable local/rural-road signing/marking guidance;
- project/agency-specific manuals where required.

Recommended initial library groups:

### Pavement markings
- solid/dashed/double lines;
- edge lines;
- stop/yield lines;
- directional arrows;
- U-turn arrows;
- zebra crossing;
- hatch/chevrons;
- parking/bus/bike/motorcycle markings.

### Traffic control
- basic regulatory signs;
- basic warning signs;
- guide-sign starter components;
- signal poles/heads;
- delineators/bollards;
- cones;
- guardrail/barrier families.

### Roadside/presentation
- streetlights;
- bus shelters/stops;
- railings/fences;
- common Thai-context vehicles;
- trees/landscape;
- simple building massing.

## Asset production policy

For every needed asset, use this order:

1. Can it be generated procedurally from semantic parameters?
   - If yes: generate it in code.
2. Can it be built as a reusable semantic assembly from simple components?
   - If yes: use assembly components.
3. Can an original vector/simple 3D asset be created through the project pipeline?
   - If yes: generate and normalize it.
4. Otherwise use a permissively licensed third-party asset after license review.

The user should not be asked to manually draw SVG, model GLB, UV unwrap, create thumbnails, or edit raw asset metadata.

## Third-party asset policy

- Prefer CC0 or permissive commercial-use assets for generic context content.
- Preserve author/source/license metadata.
- Do not copy assets from Streetcraft, RoadRunner, 3DStreet, games, CAD libraries, or competitor packages without explicit license confirmation.
- Keep asset provenance auditable.
- Consider SPDX/REUSE-style machine-readable license records for the repository.

## 3D runtime format

Use glTF/GLB as the default runtime/interchange candidate for 3D presentation props.

Requirements for normalized GLB assets:
- meters as physical scale;
- predictable forward/up orientation;
- sensible pivot/origin;
- bounded triangle count;
- bounded texture resolution;
- PBR-friendly materials;
- optional LOD metadata later.

## Library UX

The user should interact with semantic categories, not file paths.

```text
Library
  Road Markings
  Traffic Control
  Roadside
  Vehicles
  Landscape
  Buildings
  User Assets
```

Features:
- search;
- category filter;
- thumbnail/2D preview;
- drag/place;
- recent/favorite later;
- asset metadata/details;
- source/license info available without cluttering normal workflow.

## Non-goals for the initial asset system

Do not block core engineering development on:
- photorealistic AAA vehicles;
- large human character libraries;
- botanical-quality vegetation;
- full country-wide sign catalog;
- animation rigs;
- complex BIM assets.

Start with a small, dimensionally credible, stylistically coherent library and expand through the same metadata/pipeline rules.
